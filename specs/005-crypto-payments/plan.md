# Implementation Plan: Crypto Payments (Requirement 2.4)

**Branch**: `005-crypto-payments` | **Date**: 2026-11-27 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/005-crypto-payments/spec.md`

## Summary

Buyers pay orders in mUSDT on Sepolia from MetaMask; the platform recognises the transfer and
marks the order Paid; unpaid orders expire after 30 minutes and return their stock. Approach:

- **One chain watcher in the shop-operator** (research R1–R3): a leader-elected loop reads mUSDT
  `Transfer` logs to all Wallet addresses in one paged query per ≤10-block range, only up to
  `head − 6`, every 12 s, and posts each shop's transfers plus "seen through block/time" to that
  shop's internal endpoint. Cursors live in Wallet status.
- **The shop app matches and expires** (R4–R7): one atomic step per transfer (paid or recorded
  as unmatched) and per expiry, on PostgreSQL and Redis; expiry only behind the delivered
  "seen through" time; one waiting order per paying account.
- **004 follow-ups**: D-1 extends the Wallet finalizer (rollout done and 0 waiting orders, R9);
  D-4 adds a Shop finalizer that orphans and re-adopts data unless ShopHub annotated the delete
  (R11); D-5 tightens readiness (R10); D-6 makes ShopHub ignore a status older than the spec
  (R12).
- **Token**: `MockUSDT` (6 decimals, open mint ≤ 1,000 per call) in shop-operator, tested on
  Anvil; deployed once by hand with Remix (R8).

## Technical Context

**Language/Version**: Go 1.26 (shop-operator), .NET 10 + Angular 22 (shop, shophub), Solidity
0.8.x pinned (token)

**Primary Dependencies**: controller-runtime (existing), go-ethereum v1.17 (already a dependency
for 002 key generation; here `ethclient` for JSON-RPC and log types, no keys), testcontainers-go
(new, for Anvil); OpenZeppelin Contracts ERC20 (pinned); existing Npgsql /
StackExchange.Redis in shop; no wallet library in the browser (EIP-1193 calls, three fixed
selectors)

**Storage**: shop PostgreSQL (CNPG) or Redis per shop (orders, payments, chain progress);
Wallet status for watcher cursors; no new datastore

**Testing**: shop — xUnit + Testcontainers (PostgreSQL, Redis); shop-operator — envtest +
testcontainers-go Anvil with the committed token bytecode; shophub — existing unit/API/k3s
tests; CI never contacts Sepolia (Principle IV)

**Target Platform**: Docker Desktop Kubernetes; Ethereum Sepolia for the live check only

**Project Type**: existing services (operator, web app ×2) + one small contract

**Performance Goals**: Paid ≤ 2 min after MetaMask confirmation (≈ 72 s of confirmations + ≤ 12 s
poll + delivery); expiry ≤ 1 min after deadline (15 s job); catch-up of 1 h ≤ 5 min

**Constraints**: free provider plan (≤ 10 blocks per log query, modest request quota): one
query per range for all Wallets; no private keys anywhere in the platform; RPC URL only in a
hand-made Secret

**Scale/Scope**: local cluster, ≤ 5 shops per owner, a handful of Wallets; tens of orders

## Complexity Tracking

| Item | Why Needed | Simpler Alternative Rejected Because |
|------|------------|-------------------------------------|
| Solidity + OpenZeppelin (outside the technology list) | Principle IV requires a project-owned mUSDT | Using an existing token isn't "project-owned" and may have no open mint |
| **Manual M1: provider account** | The platform needs a Sepolia endpoint; accounts can't be created from code | Running a Sepolia node (heavy storage and sync) |
| **Manual M2: RPC Secret** `shop-operator-rpc` | The URL contains an API key (Principle VI); like the Discord token it is made by hand once per cluster | Storing it in git or CI (forbidden) |
| **Manual M3: Remix deploy** from the maintainer's MetaMask | One-time deploy without storing a deploy key anywhere (clarification Q2) | CI deploy needs a funded key in CI and contacts Sepolia (Principle IV) |
| D-4 orphan/adopt of data on an unrequested Shop delete (Principle V effect) | Kubernetes can't undo a delete; keeping data objects alive across the gap is the only way to restore the same shop (004 D-4) | Holding the Shop in Terminating forever (ShopHub can't recreate it); a validating webhook (certificates and a webhook server for one rule). Proposed constitution PATCH: "deleting that resource through ShopHub removes them; an unrequested delete keeps the data for re-adoption" |
| Hand changes in live checks (operator scaled to 0; Shop deleted by hand) | Scenarios 6 and 8 need an outage and a mistaken delete | No other way to cause them on a real cluster |
